# Создание постов с inline-кнопками

## Цель

Добавить владельцу бота безопасный пошаговый сценарий публикации поста с изображением, подписью и одной или несколькими URL-кнопками в основной канал `CHANNEL_ID`.

## Доступ и запуск

- Команда `/post` доступна только пользователю с ID из `ADMIN_LOG_CHAT_ID`.
- Сценарий работает только в личном чате владельца с ботом.
- `/cancel` отменяет активный сценарий на любом шаге.
- Повторный `/post` удаляет незавершённый черновик и начинает новый.
- Callback-кнопки сценария дополнительно проверяют ID пользователя и личный чат.

## Пользовательский сценарий

1. Владелец отправляет `/post`.
2. Бот читает данные текущего `CHANNEL_ID` через Telegram API и показывает кнопку с названием канала.
3. После выбора канала бот просит прислать одно фото с непустой подписью.
4. Бот сохраняет идентификатор сообщения с фото и просит текст первой кнопки.
5. После текста бот просит URL кнопки.
6. URL должен использовать схему `http` или `https`. После успешной проверки пара «текст + URL» добавляется в черновик.
7. Бот предлагает «Добавить ещё» или «Готово».
8. При выборе «Добавить ещё» повторяются шаги ввода текста и URL.
9. При выборе «Готово» бот отправляет владельцу превью: копию исходного фото с подписью и всеми URL-кнопками. Каждая URL-кнопка находится на отдельной строке.
10. Под превью расположены управляющие кнопки «Опубликовать» и «Отмена».
11. «Опубликовать» копирует исходное сообщение в `CHANNEL_ID`, добавляя итоговую клавиатуру. После подтверждённого Telegram API успеха бот сообщает о публикации и удаляет черновик.
12. «Отмена» удаляет черновик без публикации.

Минимальное число URL-кнопок — одна. Альбомы и публикации без картинки в эту версию не входят.

## Архитектура

### Регистрация обработчиков

Отдельный модуль публикации регистрируется в `src/bot.ts` после команд и до LLM-обработчика. Он содержит обработчики команды, сообщений активного сценария и callback-запросов с собственным префиксом данных.

Middleware области видимости продолжает пропускать личные сообщения владельца. Обработчик публикации игнорирует все обновления, которые не принадлежат активному черновику, чтобы обычный LLM-режим сохранил текущее поведение.

### Модель состояния

Черновик хранится в Upstash Redis под ключом, содержащим ID владельца. Состояние включает:

- текущий шаг;
- выбранный `channelId`;
- ID личного чата и ID исходного сообщения с фото;
- временный текст ещё не завершённой кнопки, если он введён;
- массив готовых пар `{ text, url }`;
- время создания или TTL.

Шаги образуют конечный автомат: `select_channel`, `await_post`, `await_button_text`, `await_button_url`, `choose_next`, `preview`.

TTL черновика — 24 часа с последнего успешного шага. После истечения срока владельцу предлагается снова выполнить `/post`.

### Формирование публикации

Для превью и публикации используется `copyMessage` исходного фото. Так сохраняются подпись, форматирование и Telegram file reference без скачивания файла ботом. В `reply_markup` передаётся заново собранная `InlineKeyboard`; каждая кнопка завершается переносом строки.

Управляющие кнопки превью отправляются отдельным сообщением-ответом, потому что клавиатура самого превью уже занята пользовательскими URL-кнопками.

## Проверки и ошибки

- На шаге поста принимается только одиночное фото с непустой подписью.
- Пустой текст кнопки и текст вне ожидаемого шага не изменяют состояние.
- URL разбирается стандартным `URL` и принимается только при протоколе `http:` или `https:`.
- Ошибка `getChat` не позволяет выбрать канал и выводит понятное сообщение.
- Ошибка копирования превью оставляет черновик активным, чтобы действие можно было повторить или отменить.
- Ошибка публикации не удаляет черновик и сохраняет кнопку повторной публикации.
- Повторное нажатие «Опубликовать» после успешной очистки черновика не создаёт второй пост и отвечает, что сценарий уже завершён.
- Callback всегда получает ответ, включая устаревшие и неавторизованные нажатия.

## Тестирование

Реализация ведётся через TDD. Модульные тесты покрывают:

- переходы каждого шага конечного автомата;
- доступ только владельцу и только в личке;
- требование фото с подписью;
- проверку URL;
- добавление нескольких кнопок отдельными строками;
- превью через `copyMessage`;
- успешную публикацию и очистку состояния;
- сохранение состояния при ошибке Telegram API;
- отмену, перезапуск и устаревшие callback-запросы;
- отсутствие передачи сообщений активного сценария в LLM-обработчик.

После модульных тестов выполняются полная проверка типов и весь тестовый набор проекта. Финальная ручная проверка проводится на staging-боте с тестовым каналом перед production-деплоем.
